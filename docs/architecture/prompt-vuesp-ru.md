# Промт для ИИ — прошивка `vuesp` и контракт устройства

Сначала прочитай [общий архитектурный контекст экосистемы](./ecosystem-master-context.md). Работай только с этим репозиторием прошивки и частью архитектуры экосистемы, относящейся к контракту устройства.

## Цель

Спланировать обратно совместимый контракт устройства и путь развития прошивки, чтобы `vuesp-app` мог обнаруживать устройства, отображать типовые сущности, проверять команды и в дальнейшем передавать нормализованные данные локальным интеграциям и в облачную телеметрию, включаемую только с согласия пользователя.

## Область работы

- Изучи текущую прошивку, целевые платы, обнаружение устройств, сообщения WebSocket, хранение идентификатора и конфигурации, команды, встроенный интерфейс, а также существующую конфигурацию сборки и тестов.
- Предложи версионируемые протокол устройства и manifest, а также стратегию совместимости с уже выпущенными прошивками Vuesp.
- Определи стабильные идентификаторы проекта и устройства, передачу версии прошивки, модели платы и возможностей, семантику сущностей, схемы команд, поведение ACK/error и тайм-аутов, а также валидацию manifest.
- Сохрани UDP discovery и бинарный WebSocket как начальный транспорт; контракт устройства не должен зависеть от конкретного транспорта.
- Определи жизненный цикл постоянного UUID: он сохраняется после обновления прошивки и обычного сброса настроек; меняется только при явном сбросе идентичности; полное стирание NVS приводит к созданию нового UUID.
- Оставь hardware/chip ID локальными диагностическими или миграционными данными, а не публичной идентичностью. Не проектируй передачу hardware ID в облако.
- Опиши поддержку legacy: текущие команды и встроенный интерфейс остаются доступными; не угадывай значения полей для MQTT/cloud mapping.
- Зафиксируй семантику команд: request ID и ACK/error/timeout; без очереди команд при отключённом устройстве и без воспроизведения команд после переподключения; повтор с тем же request ID разрешён только для идемпотентных set-команд; кнопки и импульсные действия автоматически не повторяются.
- Включи информацию о пакете прошивки для конкретной платы, необходимую web flasher сайта (целевая плата, offsets, обязательные образы), не реализуя сам flasher.
- Исключи OTA из MVP.

## Согласованное направление WebSocket/dashboard для hub

- Hub инициирует WebSocket-соединение после добавления устройства пользователем. Сохранённые устройства автоматически переподключаются с увеличивающейся задержкой.
- В новом протоколе используй версионируемые JSON control-кадры в том же WebSocket для handshake/описания устройства, manifest и конфигурации dashboard, а также ответов ACK/error на команды. Бинарные кадры можно сохранить для состояния и телеметрии.
- Описание устройства передаёт по WebSocket `schemaId`/версию бинарного декодера `struct`; hub использует встроенный реестр поддерживаемых декодеров. Отдельный HTTP-запрос за метаданными протокола не требуется. Для новых бинарных схем декодер необходимо добавить в hub; неизвестную схему нельзя угадывать или декодировать вслепую.
- Последовательность подключения: hub отправляет `HELLO` со списком поддерживаемых версий протокола; устройство отвечает описанием (идентичность, прошивка/плата, версия схемы struct/декодера, capabilities); затем hub отдельно запрашивает manifest и dashboard, проверяет их и запрашивает начальный snapshot состояния. Общие команды остаются отключёнными до успешной проверки manifest. Точные имена сообщений и схемы payload согласуются совместно с hub.
- `struct` описывает только кодирование и декодирование бинарных данных. Версионируемый manifest является источником истины для стабильных ID сущностей, их типов и типизированных команд.
- Конфигурация dashboard — декларативное представление: порядок, подписи, тип/параметры виджетов и ссылки на ID сущностей/команд из manifest. Она не переопределяет семантику сущностей или команд.
- Считай конфигурацию устройства недоверенными данными. Никогда не исполняй встроенный JavaScript и не импортируй исполняемые модули с устройства.
- Сохраняй поддержку выпущенных прошивок с бинарным протоколом через явные legacy-адаптеры. Сопоставляй только известные legacy-поля и команды; неподдерживаемые или несопоставленные данные оставляй только для чтения либо не показывай. При неизвестной major-версии manifest устройство остаётся видимым, но общие команды и интеграции отключаются.
- Формат передачи и семантика новых типизированных команд пока не определены и должны проектироваться совместно с hub; не выводи их из legacy-протокола.
- Для новых бинарных схем потребуется согласованный выпуск прошивки и hub с регистрацией соответствующего `schemaId`/декодера.

## Вне области работы

- Реализация hub, сайта, системы аккаунтов, облачного backend, MQTT broker или web flasher.
- Нарушение совместимости с выпущенными прошивками без явного плана миграции.
- Добавление шифрования или аутентификации транспорта без согласования: принятое ограничение доверенной LAN нужно документировать, а дальнейшее усиление безопасности описывать отдельно.

## Порядок работы и результаты

1. Изучи репозиторий и опиши текущее поведение протокола и прошивки со ссылками на файлы.
2. Выяви риски совместимости, неизвестные решения, относящиеся к задаче тесты и конфигурации сборки.
3. Предложи контракт, структуру manifest, версионирование протокола и схем, стратегию миграции/поддержки legacy и последовательность реализации с измеримыми критериями готовности.
4. Отдельно перечисли нерешённые вопросы; прежде чем принимать решения, влияющие на совместимость, безопасность или поддержку оборудования, уточни их у владельца.
5. Не редактируй код до явного подтверждения реализации; остановись и дождись такого подтверждения.

После подтверждения реализуй только согласованные этапы, сохрани существующие изменения в рабочем дереве, добавь или обнови относящиеся к задаче тесты и документацию, затем сообщи точные результаты проверок.
